## 1. Available API and the remaining decision

`exec_command` exposes command/cwd/shell/login/tty/yield_time_ms; `write_stdin` resumes a returned session. Neither supplies a host pre-spawn monotonic deadline, passable Unix FD, process handle/pidfd or guaranteed wall-time kill. `yield_time_ms` only yields control. Tool session IDs and stdout are not exit proofs; a final tool exit is evidence of its command, not every detached descendant. No combination of these APIs alone guarantees physical termination before the first Python instruction. Python also documents that process creation may delay timeout handling: [subprocess documentation](https://docs.python.org/3.14/library/subprocess.html).

Therefore do not implement the old hypothetical provider-FD handoff as if it exists. Two explicit choices remain:

- **Recommended safety contract if controller permits it:** conservatively account the complete newly created command-process lifetime, reject before target on exhausted/unknown startup, enforce remaining deadlines once the owner runs, and retain unknown on startup/syscall stalls. Accept success only with a known timely terminal and all bindings. This is startup-inclusive acceptance/accounting, **not** a guaranteed physical stop while Python has not initialized. It needs a specific ruling that this meets the actual gate despite that unavoidable limitation.
- **If physical startup backstop is mandatory:** keep actual closed until the provider exposes a documented owned-process absolute timeout or an independently provisioned trusted watchdog/caller is reviewed. Adding GNU timeout, another Python launcher or a prepared GO phase does not establish the missing bound on that launcher's own startup. No such infrastructure is currently authorized or claimed available.

Do not silently choose the first contract. The following is a bounded candidate for it; it is not actual permission.
