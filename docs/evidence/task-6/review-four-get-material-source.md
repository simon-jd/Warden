### Important

**I1 — Failure serialization can replace an actual returned array through an inherited `toJSON`.**

- **Location:** `docs/evidence/task-6/controller-four-get-material-source-caller-candidate.js:112`, with serialization at `:117` and failure-envelope construction at `:130`. The identical frozen execution-plan code is at `docs/evidence/task-6/continuation-controller-operations-execution-plan.md:461`. The relevant fixture gaps are `controller-four-get-material-source-caller-fixture.js:13` and its cases at `:32` and `:36`.
- **What is wrong:** `exactJSON` handles `Array.isArray(x)` first, checks only own-key count, holes and element values, and returns before the ordinary-object prototype check. It therefore accepts a dense array with a custom prototype. `JSON.stringify` subsequently consults an inherited callable `toJSON`, which can return different data. The function's comment promises refusal of lossy serialization and no stripping of actual tool data, but this branch does not enforce that promise.
- **Concrete static path:** let the initial tool return an array whose only own keys are index0 and length, whose element is the string `actual-invalid-response`, and whose custom prototype inherits Array.prototype and defines `toJSON()` returning `{exit_code:0}`. `nativeCall` stores the actual array at `:74`. `response` correctly rejects it because it is an array, stopping the normal GET workflow. The catch then calls `failureSave`. The nested response passes `exactJSON`'s array branch because its own keys and element are acceptable. `JSON.stringify` invokes the inherited `toJSON` and writes `response:{"exit_code":0}` into the nonauthority failure envelope instead of the array that actually returned. The caller can then complete that diagnostic save normally, without selecting outer-retention-only.
- **Requirement and impact:** M8 at `controller-four-get-material-one-shot-ruling.md:7` requires retaining every actual value, including invalid responses, and leaving non-JSON/unrepresentable values unknown in the external record rather than repairing them. This is a specific evidence-integrity violation in the failure workflow that is explicitly in this review's scope. It does **not** bypass Python material authority, run a successor or turn `authority:false` into success. It does make the saved request/response history differ from the actual returned value precisely when the defensive path is supposed to preserve that value. The Important severity applies to the complete exact-caller evidence contract, not to a claimed private-operation exploit.
- **Why the existing JS cover does not answer it:** `patch-foreign-prototype` exercises a non-array patch result and is caught by the ordinary-object branch. `array-properties-retained-externally` adds an own property, which the new own-key count rejects. Neither covers an array with ordinary own keys but a custom prototype/inherited serialization hook. The fixture's `clone` creates `[]` for every array at `:15`, so it also discards custom array prototypes from stored snapshots; a new test must not accidentally normalize the input it intends to check.
- **Fix:** reject unsupported array prototypes/serialization hooks before calling JSON.stringify, preserving the selected conservative ordinary-JSON profile rather than adding coercion. A focused generated case should return the custom-prototype array through the real frozen caller, require normal progression to stop, require no diagnostic patch containing a transformed response, and require outer-retention-only with the original malformed value retained by the test model. Keep the candidate and complete plan code identical and preserve the old failed/passing evidence. No native material execution or broad203-method rerun is needed to demonstrate this caller-only defect unless the eventual fix also changes native source.
- **Verification boundary:** this finding follows from the inspected JavaScript control flow and JSON serialization semantics. I did not execute the caller, a JS reproduction or any test. The full static witness above is reviewable without asserting that such a return has occurred in the real tool runtime.
