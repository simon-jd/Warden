## Metadata policy and two-address interpretation

The original prose names Azure/GCE-style `169.254.169.254` and the GKE metadata server without a second literal. Official [GKE documentation](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity) identifies `169.254.169.252:988` on its non-Dataplane-V2 path; Dataplane V2 uses `169.254.169.254:80`. Preserve both `/32` addresses as denied regression destinations. Only `169.254.169.254:80` is Azure IMDS. `169.254.169.252:988` has no Azure metadata-service equivalence; its absence on Azure/home k3s is not passing enforcement evidence. `metadata.google.internal` is a GKE name, not an Azure endpoint. Do not substitute Azure `168.63.129.16` as a second IMDS address; it is a distinct platform-service address and requires separate service analysis if ever in scope.

Source policy design: namespaced CiliumNetworkPolicy in every trusted sandbox namespace, `endpointSelector:{}`, `egressDeny` to both exact `/32` CIDRs with no port restriction. All-address/protocol denial prevents alternate-port bypass. Retain independent default-deny egress and only reviewed future allow rules; never add `0.0.0.0/0` merely to make a deny example look functional. Explicit Cilium deny wins over allow policies; standard Kubernetes NetworkPolicy exceptions alone can be overridden by additive allows. [Cilium deny semantics](https://docs.cilium.io/en/stable/security/policy/deny/). Source checks must cover namespace selection and drift/admission authority, not just CIDR strings.

Azure IMDS uses HTTP, requires `Metadata:true`, a supported API version, and proxy bypass; malformed-header403/400, refused connections or absent routes are not policy denial. Future positive controls use a noncredential fixed metadata path, discard response bodies and use no identity/oauth2 token endpoint. Disable redirects and inherited proxies; use canonical numeric addresses, short bounded connection/request deadlines and fixed requests. Record transport result versus HTTP response separately. [Azure IMDS behavior](https://learn.microsoft.com/en-us/azure/virtual-machines/instance-metadata-service).

Actual Cilium prerequisite: CRDs/controller and agents ready on the relevant nodes, selected Pod has a Cilium endpoint/identity, applicable policy realized at its revision, correct destination routing, supported kernel/CNI, no unreviewed redirect/proxy or hostNetwork bypass. Generic [k3s/Cilium installation](https://docs.cilium.io/en/stable/installation/k3s/) requires replacing the default CNI and disabling competing network policy. That is not authorization to change this host or the stopped lab profile. Standard Kubernetes [network-policy hostNetwork behavior](https://kubernetes.io/docs/concepts/services-networking/network-policies/) is implementation-dependent; enforce `hostNetwork:false` for all sandboxes. Host policies are a separate design, not an assumed consequence of namespaced CNP.

[AKS Azure CNI Powered by Cilium](https://learn.microsoft.com/en-us/azure/aks/azure-cni-powered-by-cilium) currently documents L3/L4 CNP and clusterwide policy without ACNS, while FQDN/L7 and managed flow-log observability require ACNS. Choose only supported basic L3/L4 semantics, pin actual versions later, and do not depend on paid Hubble/ACNS evidence. Its standard/manual cluster option must not be confused with purchasing the prohibited AKS Standard pricing tier. AKS Automatic examples include a managed NAT gateway and are not an approved deployment route.
