## Verified primary-source findings

All sources below were retrieved 2026-10-25. Facts concern documented/source behavior, not this machine, account, tenant, or deployed versions.

* **Azure root authentication, fact:** the [Azure API](https://developer.hashicorp.com/vault/api-docs/secret/azure) marks `identity_token_audience` and `identity_token_ttl` Enterprise-only. [Vault 1.17 release notes](https://developer.hashicorp.com/vault/docs/v1.17.x/release-notes/1.17.0) introduce plugin identity tokens; this historical feature floor does not make it Community functionality. There is no identified minimum Community version satisfying the entire home-k3s/no-static-root-secret requirement.
* **Exact implementation, fact:** pinned [Azure plugin v0.25.0 provider.go](https://raw.githubusercontent.com/hashicorp/vault-plugin-secrets-azure/v0.25.0/provider.go), `getTokenCredential`, selects a client-secret credential when present, otherwise a client-assertion credential when the plugin audience is configured, otherwise `ManagedIdentityCredential`. Its assertion callback calls Vault `GenerateIdentityToken`; it does not read a projected Kubernetes assertion file. The inspected path does not instantiate `WorkloadIdentityCredential`, `DefaultAzureCredential`, or Azure CLI credentials. Merely setting `AZURE_FEDERATED_TOKEN_FILE` is therefore not a supported solution. This tag is a research pin, not an approved installed version or a proven Vault/plugin compatibility pair. Revalidate the exact bundled plugin before any future material selection.
* **Directory and permission behavior, fact:** [Azure engine documentation](https://developer.hashicorp.com/vault/docs/secrets/azure) associates dynamic SPs with leases, deleting them on expiry/revocation; an existing-SP role instead creates/removes passwords. Its documented dynamic flow lists Graph `Application.ReadWrite.OwnedBy` and `GroupMember.ReadWrite.All`, and illustrates subscription User Access Administrator. It explicitly labels plugin WIF Enterprise and requires Azure-reachable Vault issuer/JWKS endpoints. These example privileges are not authorized defaults. No-group operation may avoid group writes, but that narrower exact plugin/API permission contract remains to be proved. Explicit role-definition IDs should avoid name lookup; exact RG-only role-assignment authority still needs validation. Root rotation would retain a secret and can widen Graph requirements, so it does not resolve this task.
* **Kubernetes lifecycle, fact:** [Kubernetes auth](https://developer.hashicorp.com/vault/docs/auth/kubernetes) documents periodic rereading of the in-pod reviewer token from Vault **1.9.3+**. This is the minimum demonstrated feature floor for the proposed short-lived reviewer design, not a recommendation to deploy an obsolete release. The selected future Community release must be security-maintained and pinned with its built-in plugins. External-Vault client-as-reviewer mode instead grants each client TokenReview authority; JWT auth has different early-revocation behavior and cannot silently replace the required Kubernetes auth.
* **Local HA, fact and inference:** [integrated Raft storage](https://developer.hashicorp.com/vault/docs/internals/integrated-storage) supports majority quorum and common seal configuration. Three local voters tolerate one process loss; all three on home-ubuntu share one machine failure domain. Accordingly this is a process-failover lab, not host-level HA. A single node may be a later DB-functional subprofile but cannot pass the original HA claim; two nodes give no single-node failure tolerance.

Entra Free capability does not remove the Vault edition boundary. Task 7's proposed k3s issuer is also not Vault's plugin issuer: issuer, subject and signing authority differ. No public endpoint, signing-key export, Blob upload or directory trust is authorized here. Tenant app-registration policy, consent, directory quota and ability to constrain all permissions remain UNKNOWN. Dynamic application/SP objects are Entra directory objects, not children of `rg-warden-lab`; ARM RG deletion does not establish their cleanup. Graph string tags do not satisfy ARM's four resource tags. This literal-only-RG conflict requires explicit scope resolution before any directory mutation, even if ARM role assignments are RG-scoped.

## Proposed local trust and bootstrap boundary

Propose three isolated, non-dev Vault Community processes/pods with TLS, separate Raft directories, unique node IDs and bounded audit files. In an explicitly approved future Kubernetes profile, use a dedicated Vault reviewer SA, a short-lived automatically renewed projected token, and the narrow TokenReview permission. Bind the control-plane login role to one exact namespace and SA with an explicit Vault audience. Configure and validate the Kubernetes API TLS endpoint/CA, TokenReview audience result, and SA identity. The [auth API](https://developer.hashicorp.com/vault/api-docs/auth/kubernetes) exposes these bindings. Vault-side issuer checking defaults changed historically; using TokenReview with `disable_iss_validation=true` delegates issuer validation to the trusted API, not to an arbitrary issuer URL. Never disable API TLS verification. Confirm the actual issuer and token-request/projection configuration before admission.

Use a separate projected assertion for Azure exchange if that path is ever resolved; the Vault login audience and `api://AzureADTokenExchange` are not interchangeable. Keep sandbox SAs and containers outside Vault login, reviewer, DB, directory and audit permissions. Task 7's real SA/FIC/RBAC/metadata/AKS gates remain unproved. Existing host k3s/network configuration is not authority to install or mutate a cluster; client-as-reviewer is an explicit alternative requiring review, not a fallback when the reviewer expires.

Later bootstrap must specify TLS issuance, initialization, custody of Shamir shares, operator authentication, root-token revocation, DB-owner provisioning, scoped policies and teardown. Unseal shares and local signing keys are essential trust material, not Azure client credentials; their protected custody must be separately designed. Do not run dev mode or leave a reusable root token in env, manifests, repository, Terraform state or evidence. A restricted PostgreSQL management identity may still be required for dynamic SQL roles; document and rotate its credential within Vault after one-time bootstrap, remove bootstrap copies, and never call that credential absent. If the intended requirement prohibits every persistent local DB-management credential too, this is a separate unresolved requirement, not covered by the cloud-key audit.

## Database lease contract and exact acceptance

The [PostgreSQL engine](https://developer.hashicorp.com/vault/docs/secrets/databases/postgresql) supports dynamic roles with password expiration interpolated into creation SQL. Proposed production settings: default TTL **<=3600 seconds**, max TTL **<=14400 seconds**; explicit isolated test role default/max **60 seconds** and no renewal. Use SCRAM password authentication with verified TLS. Dynamic roles get only required DML on the designated schema and no DDL/object ownership, role creation, superuser or bypass-RLS authority. The current startup migration needs a separate migration identity/phase; do not grant it to every application lease just to preserve existing main startup behavior.

[PostgreSQL VALID UNTIL](https://www.postgresql.org/docs/current/sql-createrole.html) expires passwords, and does not restrict non-password authentication. The future pg_hba contract must exclude trust/peer/certificate alternatives for the tested user. Preserve three separate observations: ability to establish a **new password-authenticated connection**, behavior of an **existing SQL session**, and Azure **already-issued access tokens**. They are not equivalent revocation properties.

Controller-supplied integration constraint: the proposed Task 6 fixed PG harness uses a private UNIX socket with trust only for `warden_test` role/database and rejects other roles. It cannot supply Task 8 password-expiry evidence: its trusted identity bypasses password checking and its dynamic roles would be rejected even before expiry. Task 8 therefore needs its own separately reviewed exact SCRAM/authentication profile and pre-expiry/revoke successful fresh-login controls. No change to Task 6's harness or actual profile is authorized by this proposal.

1. **`TestDynamicCredsExpire`:** real Kubernetes-auth login to real Vault; acquire a fresh 60-second credential; establish a new DB connection and perform a permitted query before expiration; observe the lease duration and server role-validity timestamp without selecting a password hash. After the authoritative deadline, make a fresh uncached TCP/TLS password connection and require an authentication/invalid-role rejection. Bracket that attempt with a separately valid control credential proving the same database is reachable and healthy. A timeout, network failure, closed pool, elapsed sleep, absent Vault lease, or locally rejected expired credential is not expiry proof. Clock uncertainty produces NOT_PROVEN rather than extending the credential's permitted life. Bounded polling is only scheduling; each acceptance observation is an actual new login. Also observe bounded eventual role cleanup separately.
2. **`TestLeaseRevocation`:** independently create a working fresh credential, then call exact-lease `/sys/leases/revoke` with `sync=true`. The [lease API](https://developer.hashicorp.com/vault/api-docs/system/leases) defaults to queued revocation; synchronous mode returns after completion. Immediately after successful return, without grace sleep or retry-until-pass, require the first new DB login to fail authentication while a valid control login succeeds. Define the request deadline and record timing; a timeout leaves outcome UNKNOWN, not revoked. Never use revoke-force, broad prefix deletion or removal of bookkeeping as proof. Revocation SQL must first disable login/expire the generated role, then remove only its grants and role; prove retries are safe on the exact managed role. Partial SQL failure is not successful cleanup.
3. Existing SQL sessions may remain usable after password expiry. Record that separately and close/drain the control-plane pool before its lease deadline; if immediate session termination is required, add a separately authorized, narrowly privileged session-kill policy and explicit test. Do not relabel new-login rejection as termination of existing sessions. A session test failure cannot be hidden by pool recycling.

Propose a small internal credential provider returning only in-memory DB credential material plus lease ID/deadline, with injected HTTP transport and clock. Integrate at the existing pgxpool creation boundary after source ownership release; repositories and run stores can retain their current pool interfaces. A trusted lifecycle owner acquires a lease, pings before exposing a replacement pool, stops new work before its deadline, drains/closes old sessions, and requests exact-lease cleanup. No secret DSN or arbitrary backend error text reaches audit/logs. Avoid a generic secret broker, nonexistent Task 6 store APIs, or assuming renewal preserves a four-hour maximum; initially prefer bounded new-lease rotation.

The narrow states needed are `NOT_ISSUED`, `ACTIVE`, `STOPPED`, `REVOKE_PENDING`, `REVOKED`, `UNKNOWN`. Issuance is a write despite its HTTP read shape: timeout after remote creation can leave an unknown lease. Do not blindly retry and lose ownership of duplicate credentials; stop admission and reconcile through a separately scoped operator capability. `REVOKED` requires verified exact-lease backend completion; if role removal fails retain cleanup pending. Future Azure state additionally tracks exact app/SP/credential/role-assignment identifiers; directory propagation and partial cleanup cannot be collapsed to success. This is a proposal for ownership bookkeeping, not a new recorder/journal implementation.

Deleting an Azure SP/password does not establish immediate rejection of an access token already issued to it. Task 7's actual `exp-iat <=3600` conflict remains independent of the DB 60-second test and production DB lease TTL. Neither a one-hour Azure password nor a short Vault lease shortens an Azure access token. Future Azure tests must distinguish new token acquisition, already-issued-token resource access, ARM assignment cleanup and Graph object cleanup, and report the actual observed result.

A few supplied object IDs prove only those IDs. Claiming complete project coverage additionally requires an independently authoritative inventory and reconciliation of all project-owned/generated objects and orphan candidates; a naming/tag filter alone is insufficient. An empty manifest or absent provider configuration is NOT_EXECUTED, never zero. Do not claim tenant-wide absence from project coverage. AWS/GCP are superseded by the Azure budget; no fabricated zero counts for unaudited AWS/GCP accounts.

| Category | Required count/decision; no secret values |
| --- | --- |

Any static root-engine password is prohibited regardless of short remaining life. Therefore literal zero-existing-cloud-keys conflicts with a Blob issuer/storage account. Encrypted storage of a credential in Key Vault does not make it short-lived. Do not fetch secret payloads to discover their meaning. |

This exposes two different possible assertions: zero prohibited **project-managed credential objects** within a complete reviewed boundary, versus zero **all extant Azure keys**. The latter cannot pass if storage accounts are included; selecting the former requires explicit agreement on the acceptance boundary and is not an automatic requirement relaxation. Expired orphan long-lived records remain counted as extant hygiene failures; report validity separately so they are not confused with active credentials.

For Graph, [list applications](https://learn.microsoft.com/en-us/graph/api/application-list?view=graph-rest-1.0) and [list servicePrincipals](https://learn.microsoft.com/en-us/graph/api/serviceprincipal-list?view=graph-rest-1.0) document `Application.Read.All` as their least privileged application-list permission. Even that is tenant-wide read authority and is not added automatically. Prefer authorized exact-object reads or a separately approved operator export with proven scope; inability to establish complete scope keeps the gate OPEN. Collect only IDs, typed credential metadata, dates and counts; strip hints, certificate blobs, display strings and unapproved fields at the collection boundary. [passwordCredential](https://learn.microsoft.com/en-us/graph/api/resources/passwordcredential?view=graph-rest-1.0) contains metadata and creation-only secret fields; never use creation APIs to audit. All read permissions and object visibility must be proven, not inferred from a successful first request.

Follow every approved-host/path `@odata.nextLink`/ARM continuation until terminal completion ([Graph paging](https://learn.microsoft.com/en-us/graph/paging)); reject redirects, host changes, loops and out-of-scope pages. Proposal bounds: <=100 pages, <=10,000 objects, <=1 MiB/page, <=60 seconds total, <=3 throttle retries within that total. Hitting any bound is INCOMPLETE, not a lower count. Reconcile duplicate/conflicting IDs, null/omitted arrays, 401/403/404, malformed dates and stale snapshots conservatively. A concurrent creation/deletion race prevents an atomic-zero claim; later actual collection requires a reviewed quiescent issuance window and before/after reconciliation. Soft-deleted/restorable owned objects are a separate cleanup category, not silently absent; audit permissions and restoreability need definition before final acceptance.

`TestNoLongLivedKeys` expects **0 only with complete authorized coverage** and no unknown categories. Output fixed `PASS`, `FAIL`, `INCOMPLETE`, `NOT_EXECUTED` with category counts, reviewed scope identifier and bounded timestamps; use `null` for unknown counts, never 0. Suggested exit codes 0/pass, 1/prohibited credential found, 2/incomplete or invalid input, 3/not executed. Any fixed-status result can carry a known nonzero lower bound without claiming completeness. Never print JWTs, passwords, hashes, credential hints, connection strings, SAS, HTTP bodies or arbitrary SDK errors. Fictional canary secret strings in tests must not survive serialization/error paths.
