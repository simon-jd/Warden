## What the numbers show, and what they don't

- On runc, the stock rules raised an alert in every successful run of the four tests they describe, within 0.039 to 0.109 s of the run's start, and the alert line was in the collector's file 0.003 to 0.021 s after its event. Most of the time to the event is `docker exec` starting the process in the container; the detector's own share is the delivery figure.
- **The rate is under the widest map.** An alert of any of the 25 rules on the run's container inside its execution counts. Every detected run raised exactly one alert, of the one rule that matches the test's behaviour (table above, and how well each fits its technique below it), and nothing else fired in the session; a reviewed map that names those rules would give the same counts here, but none has been written.
- **The 80% and 100% are properties of the selection.** The five attack tests were chosen because a stock rule names their behaviour, and four of them ran; this is not a sample of Atomic tests or of attacks, and says nothing about techniques no stock rule describes (the corpus round had several). The control behaved as a control: no rule fired on `hostname`, and its five successful runs are the five undetected ones in the 80%.
- **The alerts are on the command lines, not on stolen data.** The image has no `id_rsa`, no `.aws/credentials` and no real secrets: the SSH-key searches found nothing and are detected for running `find` with `id_rsa` in its arguments; shred removed the empty file its dependency created; the policy read is the image's own `/etc/pam.d/common-password`.
- **Find AWS credentials failed in every run** (exit 1, no output): `find /` cannot enter `/home/ubuntu` (0750, owned by `ubuntu`) and `/var/cache/apt/archives/partial` (0700, `_apt`) as a root without `CAP_DAC_READ_SEARCH`. A failed execution is not in the rate. The two SSH-key Atomics' `find /` meets the same two directories and fails the same way, with its errors sent to `/dev/null`; they succeed only because their scripts end in `exit 0` (the upstream text), so their "succeeded" means the search ran, not that it covered every directory. Counting Find AWS credentials as executed too would add five undetected runs: **20 / 30 (66.7%) with the control, 20 / 25 (80.0%) without**. "Find AWS Credentials" did not fire on any of its five runs either, although Falco's process rules see the `execve` whatever the exit: the rule needs `find`'s arguments to end with `.aws/credentials`, and this Atomic's end with `-type f` (`/ -path */.aws/credentials -type f`). So this Atomic, as written at this commit, is outside that rule's pattern; with no successful run that is read from the rule, not measured.
- n=5 per test, one host, one image, one container configuration, runc only. gVisor (host level) and Firecracker would not see these system calls at all (the corpus round and the runbook's limits); this round does not change that.
- Start → arrival is to the collector's `alerts.jsonl` on the same host, an upper bound, late by at most about one poll (a 10 ms sleep plus the file read, a little over 10 ms); it is not a time to any downstream consumer, and not an end-to-end incident time.
- No false-positive figure: the session's 20 kept alerts are all from the runs (no Warden lab ran), and there is no seven-day normal window.
