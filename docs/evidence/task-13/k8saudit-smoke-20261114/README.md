- **The host collector could not place 3 alerts** received during the window. At the cutoff heartbeat (18:49:35.327) they were still pending against the collector's 20 s deadline, so each had arrived after about 18:49:15.3: at the run's start (18:49:15.668) or later. They were dropped as `dropped_unresolved` by the collector's final pass at `make detect-down` (`collector.tick(final=True)`, `detect/falco/collector.py`), at 18:49:40.75, about 5 s after the cutoff, not after 20 s. Falco's tally for all 46: "PTRACE attached to process" 24, "Drop and execute new binary in container" 22. The collector keeps nothing of a dropped alert, so the rule of each of the 3 is not known.
- **They came from the pods in the kind node**: a probe after the smoke ([host-probe/](host-probe/)) shows it. On a fresh lab with the host instance only, an idle phase of 25 s had 0 unresolved alerts (10 of other containers). Then each of three rounds of the smoke's pod work (create a labelled busybox pod in `warden-lab`, `kubectl exec ... cat /etc/hostname`, delete it, wait 25 s) had exactly 3 ([host-probe/probe.jsonl](host-probe/probe.jsonl)). The collector resolves IDs through Docker, the k3s lab's API server and the cgroups nested in Warden containers. A pod's containers in the kind node are containerd containers nested in a container that is not Warden's, so it knows none of them.
- **So the host verdict "healthy" here depends on the cutoff falling before that deadline.** With the cutoff 20 s or more after the run, or with `down` before it, the 3 drops would have been inside the window: `dropped_events` 3 for the host record, which the ledger then does not count as active coverage. Without the fix below, the Stratus round would have been the same: every technique whose pods run in the kind node would have given the host instance alerts it could not place, so the host record of every such run would have shown drops. They are not alerts lost from Warden's own containers, but the ledger cannot tell them apart.
- **Fixed afterwards.** `collector.py` now looks an unknown ID up also as a cgroup nested in any running Docker container that is not Warden's, after Warden's own nested cases (the pod first, then the node). It counts what it finds there as another container's (`dropped_other_container`, and `dropped_other_nested`), not as a drop. The same probe on a fresh lab ([host-probe-after-fix/pod-rounds/probe.jsonl](host-probe-after-fix/pod-rounds/probe.jsonl)): idle 0 alerts; each of the three pod rounds 3 alerts, all `dropped_other_nested`, 0 unresolved, 0 pending. All 9 were "Drop and execute new binary in container" (the session's only rule), so that is the rule of the smoke's 3. `make detect-down`: no module or sysctl change.

## Findings recorded for the Stratus round

- **`useAsync: false`.** The instance runs with the plugin's asynchronous field extraction off. The reason is a probe on 2026-11-14 on a throwaway `warden-lab` cluster before this smoke, same build. With the default (on), alerts reached the collector 0.32 to 1.16 s after their audit line was fed (8 alerts). Off, 10 to 31 ms (6 alerts). **That probe's outputs were not kept**, so those numbers are not evidence here. This smoke ran with it off and measured 11 to 31 ms from the feed to `alerts.jsonl` (table above).
- **Correlation ID.** The wrapper sets `STRATUS_RED_TEAM_CORRELATION_ID` to its run ID (`stratus-<24 hex>`). Stratus v2.38.0 accepts only a UUID there (`resolveCorrelationID` in `v2/pkg/stratus/runner/runner.go`); for any other value it logs a warning and uses a random UUID. So its User-Agent, `stratus-red-team_<UUID>`, names no run, differs between the wrapper's two Stratus commands, and the state is not kept apart by that ID either. In a follow-up commit, the importer attributes an alert whose User-Agent contains a receipt's `correlation_id` (a UUID) to that run (runbook). The wrapper at `dd79f39` writes none, so this smoke's scoring is unchanged.
- **What label and namespace can attribute.** Requests in `warden-lab` and requests whose body carries the run labels. Not: cluster-scoped objects (ClusterRoles and their bindings, CSRs, nodes), `kube-system` (refused as a run namespace: the system's own requests there would count), and lists across all namespaces.
- **The window** is the receipt's `started_at` to `finished_at`: `stratus detonate --cleanup` (warm-up, detonation, revert, Terraform destroy) and the wrapper's extra `stratus cleanup`. Alerts of warm-up and clean-up count for the run under the widest map, and time to detect includes Stratus's start-up and, for the Terraform techniques, the downloads and `terraform apply`.
- **`k8s.persistence.create-admin-clusterrole` fails on Kubernetes 1.24 and later**, this lab's 1.34.11 included: after creating the ClusterRole, the ServiceAccount in `kube-system` and the binding, its detonation polls for a token Secret of the ServiceAccount for one minute and returns an error; Kubernetes has not created such Secrets since 1.24. Its outcome will be `failed`, and its alerts count as alerts on failed executions.
- **No stock rule is written for `dump-secrets` or `create-token`.** "K8s Secret Get Successfully" matches `get`, not the all-namespace `list`. Nothing names a token request, but the `serviceaccount` macro does not exclude subresources, so a token request (create on `serviceaccounts/token`) matched "Service Account Created in Kube Namespace" in `kube-system` in the same throwaway-cluster probe; the request is in `kube-system`, so the importer would not attribute it.
- **The wrapper as committed cannot run the pinned binary** (read from `attacks/`, not changed here): `lab_common.digest` refuses files over 256 MiB, and the v2.38.0 binary is 362,488,146 bytes. And `lab_common.command` limits every file its child writes to 8 MiB, while Stratus installs Terraform into the run's `HOME` at the start of every command (from the source; not run), which is larger.

## What this shows, and what it doesn't

- The path works end to end on this lab: an API request with a run label or in the run's namespace, inside the receipt's window, reaches the scored alerts with the stock rule that fired, and every alert can be followed to its audit event, its feed time and its arrival. Attach/Exec Pod fired on a plain `kubectl exec`, as its rule describes.
- One benign execution, three alerts: no detection rate, no latency distribution, nothing about any Stratus technique.
- The 25 syscall rules are in the map, but no syscall alert can reach this path: the host collector keeps only Warden containers' alerts, and the kind node is not one (its pods' alerts are dropped as other containers' or unresolved).
- No false-positive figure; no seven-day window.
